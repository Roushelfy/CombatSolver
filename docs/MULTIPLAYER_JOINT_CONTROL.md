# 多人联合接管：设计与可行性测量

状态（2026-10-03）：**设计与测量方案，尚未实现。** 本文所有"游戏侧事实"来自对 `sts2.dll` / `sts2.xml` 的静态阅读与上游 `feat/multiplayer` 代码，**未做运行时验证**；"启发式"部分是推理，未经测量。

## 1. 目标

所有玩家都安装本模组并同意被接管时，由一个方案规划全队每名玩家的出牌、选牌、药水和结束回合，各客户端各自执行属于自己的步骤。

上游 `feat/multiplayer` 已让模拟器支持 2–4 人，但规划只针对本地玩家，队友视为不再行动（见 [多人适配实施规划](MULTIPLAYER_PLAN.md)）。本文在其基础上补齐联合规划与跨客户端执行。

上游维护者的意见（issue #148）：该分支暂不合并；接管全队的计算量很大，"算个小怪都要好几分钟"。因此本文把**可行性测量**（第 6 节）放在任何协议实现之前，并设门槛。

## 2. 游戏侧事实（静态阅读，未运行时验证）

- 房主给各玩家的操作排序，各客户端完整模拟战斗，每步之后比对校验和（`ChecksumTracker`）。`ActionQueueSynchronizer.HandleRequestEnqueueActionMessage` 按网络发送者确定操作归属，因此每个客户端只能替自己的角色出牌。
- 战斗中的选牌由牌的拥有者所在客户端本地完成（`PlayerChoiceSynchronizer`）。
- 所有玩家同时行动，全员 ready 才结束回合；怪物攻击默认打所有存活玩家（`AttackCommand.FromMonster` 默认 `TargetingAllOpponents`）。
- 战斗随机数（洗牌、随机目标、怪物 AI、生成牌）全队共用；各玩家抽牌堆独立，所以普通抽牌不消耗共用随机数，重新洗牌、随机目标、生成牌、随机伤害才会。出牌的全局顺序因此可能影响结果。
- 模组可以定义网络消息：游戏自动注册 `INetMessage` 子类型；BaseLib 的 `ICustomMessage`、RitsuLib 的 sidecar 可用。`ShouldBroadcast` 消息经房主转发。非 `affects_gameplay` 的模组不要求各方一致，但本功能要求握手时互相确认版本。
- **不使用**：伪造消息发送者；反射调用房主私有 `EnqueueAction` 替他人注入操作。二者绕过游戏校验，易导致状态不同步。

## 3. 设计

1. **房主是指挥。** 握手后确认各端已安装同版本并同意被接管；各客户端上报战斗状态哈希（沿用 `ContinuationStamp`），全部一致才规划。
2. **规划是联合搜索**，假设所有人的操作都由方案决定（队友的选牌、指向队友的药水都纳入搜索）：
   - `PlanAction` 增加执行者 `NetId`；候选动作来自每个玩家的手牌。
   - 目标函数：全队总掉血 + 每名玩家死亡惩罚（全灭 = 败），规划 1–2 回合，有节点预算。
   - 不假设"一个玩家打完另一个再打"，交错顺序必须能被搜索到；用第 4 节的启发式降低搜索量。
   - 规划只由房主做并广播结果，不要求多机搜索确定性（搜索有时间预算和并行，本来就不确定）。
3. **执行**：房主广播有序步骤 `(执行者, PlanAction, 期望状态哈希)`；各客户端只执行属于自己的步骤，步骤间用屏障等待上一步完成；所有人的结束回合最后执行。
4. **回退**：状态对不上、有人手动操作、掉线时，全体取消并重新规划。
5. **UI**：显示"多人接管"开关与当前步骤；任一玩家可随时关闭。

已知需要解决：队友的选牌类牌（如 `Tutor`）目前被当作未知而截断预测；以队友为目标的药水被排除；`Expansion.Candidates` 里随机选队友目标用了 `Random.Shared`，需改为可复现。

## 4. 降低搜索量的启发式（推理，待 M0.5 测量）

为什么不是"翻倍"：两名玩家的序列长度各为 d，总深度约 2d；单次分支数约 2b；不做约简时搜索量约 (2b)^(2d)，且共用随机数使"谁先谁后"成为不同局面，交错数为 C(a+b, a)。Beam search 能压住一部分，但每个节点的展开更贵，beam 容易被"只是顺序不同的等价局面"占满，保持质量需要加宽。

1. **动态交换性检查（偏序约简）**：对节点上一对来自不同玩家的候选 (a, b)，用模拟器分别跑 a→b 与 b→a，比较结果状态哈希（含共用随机数位置）。相同则只保留一种顺序（按玩家编号），不同才两种都展开。结果可缓存。不手写依赖表。
2. **转置合并**：状态哈希必须包含随机数位置，使不同交错到达同一状态时自动合并（现有转置机制）。
3. **候选池**：先对每个玩家单独跑单人 beam，取各自前 K（初值 20–50）个候选序列，联合搜索主要在其组合与交错上进行；另用"以已定队友动作为前提重算"补漏。
4. **先出可用方案，后台局部改进**：先用便宜办法得到方案并可立即使用；再对方案中每个动作尝试前移 / 后移 / 换到另一玩家之后，只保留变好的。等待时间有上限。
5. **便宜剪枝**：先检查斩杀；0 费 / 纯格挡等低风险动作优先；某玩家没有有意义的出牌时提前结束其序列；beam 中对"出牌集合相同、状态相同"的节点去重。

## 5. 降级方案

M0.5 门槛不通过时（需用户批准）：各自独立使用单人求解器，只在回合结束时同步等齐。无联合搜索，算力无忧，但会忽略与队友的配合。

## 6. M0.5 可行性测量

目的：在写任何协议代码之前，回答"联合搜索是否可行"。

**场景**：分支现有的本地联机（虚拟 2 人 / 4 人，及 ENet 双进程），覆盖小怪、精英、Boss 各至少 3 场。

**对比的方案**：

| 记号 | 方案 |
|---|---|
| A | 联合搜索（含第 4 节启发式） |
| B | 依次最优：依次规划每个玩家，其余固定，迭代 1–2 轮 |
| C | 基线：每个人各自用单人求解器 |

**指标**：每回合规划耗时；搜索节点数；团队总掉血（以同一 RNG 种子回放，直到战斗结束或固定回合数）；动态交换性检查可约简的候选对比例；并行度 1 / 4 / 8 / 16 下的耗时。

**门槛**：小怪战斗每回合规划 > 约 30 秒，或质量不优于基线 C，则停止并向用户汇报，由用户决定继续、改降级方案还是终止。

**已有旁证**：上游测试记录显示，四人 ENet 全自动（仅规划本地玩家）两次初试在建局根后 120 秒内无结果，每端并行度降到 1 后才通过（见 [测试矩阵](TEST_MATRIX.md)）。这说明即使不做联合搜索，四人的搜索压力也已不小。

## 7. 开发环境适配记录

在 Windows、Steam 装在 `C:\Program Files (x86)\Steam`、通过 Steam 启动游戏的机器上跑上游测试脚本需要的改动：

- `tools/run-multiplayer-p0-enet.ps1`：新增 `-Sts2GameRoot`、`-RitsuWorkshopRoot`（默认值指向上游作者的 `D:\Steam`）、`-KeepInstance`（调试时保留私有实例以读日志）；带空格的路径传给 `Start-Process` 时需要内嵌引号。
- `tools/run-unattended-test.ps1`：私有实例里找不到 `default\1\settings.save` 时，改为只读复制 `%APPDATA%\SlayTheSpire2\steam\<账号>\settings.save`（Steam 启动的玩家没有 `default` 目录）。
- 构建：`dotnet build CombatSolver.csproj -c Release -p:CopyModOnBuild=false`，避免产物自动复制进游戏的 `mods/CombatSolver` 影响正常游玩。
